# Testing

```
pip install -e ".[dev]"
pytest -q
```

Expected: `250 passed`, in about ten seconds. No network, no .NET, no
Bonsai installation.

## What the suite checks

**`test_ground_truth.py`: agreement with Bonsai itself.** The 30 workflows in
`tests/data/bonsai_upstream` come unchanged from Bonsai's repository. Bonsai's
own tests assert which of them fail to build and which build; baghban must
report a build-breaking finding on exactly the first group, and nothing on
workflows that build and fail only at run time (division by zero), or that
reference a type that does not exist (baghban has no type catalogue and must
not guess). It must also compute the nested include property value that
`Build_NestedIncludeWorkflows_EnsureInnerPropertyIsAssigned` asserts. This is
the part of the suite that does not depend on baghban's own reading of
Bonsai's behaviour.

**`test_checks.py`: every finding in both directions.** Each finding has a
workflow on which it must fire and a nearly identical one on which it must
stay quiet. The quiet cases are the ones that matter for trust:

| Finding | Must stay quiet when |
| --- | --- |
| `SILENT_OVERWRITE` | `Suffix` is `Timestamp` or `FileCount`; `Overwrite=False` outside a loop; the file name comes from data (`PropertyMapping`); the path is a named pipe; the writer is inside a group, which is not a loop |
| `FAILS_ON_REPEAT` | the writer is in a `Defer` (subscribed once), or has a suffix |
| `DUPLICATE_OUTPUT` | the file names differ; one copy is disabled; an included module gets its own `FileName` per include |
| `DANGLING_SUBJECT` | the subject is declared in an enclosing scope, or inside a group (groups share their parent's scope); the subscriber is disabled; an unreadable include in scope might declare it |
| `DUPLICATE_SUBJECT` | the second declaration is inside a nested workflow (closest redefinition) |
| `DUPLICATE_PROPERTY` | the two are in different groups (separate workflows); one is disabled, or inside a disabled group; the DisplayNames differ |
| `MISSING_INCLUDE` | the file exists, including with backslashes, without the `.bonsai` extension, or as a nested include resolved from the top-level folder; the include is disabled |
| `DISABLED_WRITER` | the writer is enabled |

Severities and exit codes are pinned too. `SILENT_OVERWRITE` is an error
inside a loop, a warning across runs (since 0.5.0, after
neurogears/vestibular-vr#137), and info with an externalized file name.
Info findings never fail `check`, and `--strict` fails on warnings.

**`test_project.py`: module conventions**, added after the survey: Extensions
and package modules report their undeclared subjects as their interface,
test projects stay top-level, embedded includes into same-repository packages
resolve without flags, `.bonsai` folders are ignored, and include cycles are
still checked.

**`test_confirm_harness.py`** tests `confirm/confirm.py` without .NET:
baghban's prediction for every case, and the harness's judgement of
simulated outcomes in both directions, so a "NO" on a real machine means
Bonsai disagreed rather than a harness bug.

**`test_dotnet.py`: the .NET reader.** Assemblies generated by
`tests/dllkit.py` cover every index width the reader can meet: 2- and
4-byte heaps, coded and simple indexes just below, at and above their
widening thresholds, PE32 and PE32+, linked resources, native and truncated
files. dnfile, an independent parser, confirms the generated files where it
follows the standard; it widens indexes one row late, so the two exact
boundaries are pinned by ECMA-335 II.24.2.6 (and Microsoft's
System.Reflection.Metadata) alone. Separately, the reader matched dnfile on
168 real assemblies (a .NET runtime and pythonnet, from PyPI).

**`test_packages.py`: following includes into packages.** Environments
(`.bonsai/Bonsai.config`, portable `Bonsai/`, assemblies named unlike their
package), every source in order, pinning, guessing, `--fetch` against a
local server serving nuget.org's layout (no test touches the network),
missing modules in pinned and guessed versions, nested includes, unsafe
resource names, reports, provenance and the CLI.

**`test_launch.py`: launcher values and provenance.** The command line as
Bonsai's `CommandLineParser` reads it (every spelling of `--property`,
short aliases, values containing `:` and `=`, the arguments Bonsai.exe
refuses). Where a value goes, as Bonsai's `SetWorkflowProperty` sends it:
top level, dotted through groups and a named SelectMany, through a group
into an include and a group inside it (iblrig's shape), a mapping connected
to nothing. The names Bonsai
refuses: unknown, ambiguous, two properties of one name in one workflow,
a disabled group, an include named directly, an empty name; with `strict`, nothing changes. Also include values reaching
a group inside the included file (fixed in 0.4.0), `outputs`, the
provenance fields (all strings, fingerprint of the file as saved, the
caller's document unchanged), the CLI's `-p`, and that baghban does not
depend on daftar.

**`test_config.py`: marking findings as intended.** `--ignore` rules with
and without a pattern; a rule matches only its own code and files, and
marks a module's finding through the module's path. Ignoring never changes
other findings. Marked findings are listed in the summary and in `--json`,
not dropped. `baghban.toml` and `[tool.baghban]` are found above the
workflow, but not outside the repository, and not in a `pyproject.toml`
without the table. Bad files, unknown settings and unknown codes are
errors. The CLI honours `--no-config`. On Python 3.10 without `tomli`, the
error says what to install.

**`test_confirm_properties.py`** tests `confirm/confirm_properties.py`
without .NET: baghban's prediction for each of its 11 cases, and the
judgement of simulated runs in both directions.

**`test_confirm_packages.py`** tests `confirm/confirm_packages.py` without
.NET or nuget.org, with a simulated .NET lister that agrees and disagrees.

**`test_model.py`** covers the reader: namespace and type resolution,
`Combinator`/`Source`/`Disable` unwrapping, flattened property keys, scopes,
include expansion and overrides, byte-order marks, and malformed files.

**`test_diff_render_cli.py`** covers the diff (reformatting is not a change,
inserting an unrelated node does not renumber, rewired edges are reported),
the fingerprint (stable across re-saves and `Version` stamps, sensitive to
included content), rendering, and every CLI command and exit code, on the
example rigs.

## Adding a finding

1. Find the behaviour in the Bonsai source and cite the file in the check's
   docstring.
2. Write the firing fixture and at least one quiet neighbour in
   `test_checks.py`, using the builders in `tests/xmlkit.py`, which emit XML
   in the shape Bonsai's serializer writes.
3. If Bonsai's own tests say something about the case, add it to
   `test_ground_truth.py`.

## Beyond the unit tests

- `python confirm/confirm.py` runs 15 cases with the real Bonsai runtime
  (needs .NET 8). Last run: 15/15 confirmed (12 Oct 2026, macOS, Bonsai 2.9
  packages, baghban 0.4.1). `confirm/README.md` explains installing .NET on a Mac, running
  the kit, reading its output, and records every run's results.
- `python confirm/confirm_packages.py` compares the package reader with
  Microsoft's metadata reader on real Bonsai packages (needs .NET 8 and
  nuget.org). Last run: 8/8 packages identical (12 Oct 2026).
- `python confirm/confirm_properties.py` runs 11 cases of launcher
  `--property` values with the real Bonsai runtime (needs .NET 8). First
  run: 9/10 (12 Oct 2026). The NO led to `DUPLICATE_PROPERTY`. With 0.4.1:
  11/11 (12 Oct 2026).
- `python survey/run_survey.py DIR` re-runs the survey of published
  repositories; `survey/SURVEY.md` records the last run and its hand review,
  and `survey/survey-results.json` holds that run's full output. Later
  runs are kept beside it: `survey-results-0.3.0.json` (with packages) and
  `survey-results-0.5.0.json` (without, after the 0.5.0 severity change).
